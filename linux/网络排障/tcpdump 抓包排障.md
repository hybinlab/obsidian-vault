## 为什么 tcpdump 要单独一篇

网络排障走到最后，很多问题会收敛成一个终极问题：

> **包到底有没有出去？有没有到对端？对端有没有回？**

配置、日志、防火墙规则都只是"间接证据"——它们告诉你系统认为发生了什么。只有抓包能看到"实际在线路上发生了什么"，这是唯一的直接证据。这篇笔记记的不是 tcpdump 参数怎么背，是**看到抓包结果之后，怎么判断问题出在哪一环**。

## 基本用法

```bash
# 抓指定主机的所有流量（不指定网卡，抓所有接口）
tcpdump -ni any host 192.168.1.100

# 抓指定网卡上某个端口的流量
tcpdump -ni eth0 port 443

# 只抓 TCP SYN 包（三次握手的起点，用来看连接尝试而不看数据内容）
tcpdump -ni eth0 'tcp[tcpflags] & tcp-syn != 0'
```

常用参数含义：`-n` 不解析域名/端口名（更快更清晰）、`-i` 指定网卡（`any` 表示所有）、`-vv` 更详细输出、`-w file.pcap` 保存到文件供 Wireshark 分析。

## 核心武器：TCP 三次握手判读

这是 tcpdump 排障最重要的技能——通过握手报文的**出现/缺失模式**，直接定位问题在哪一层。

### 正常握手（一切正常）

```
Client → SYN
Server → SYN,ACK
Client → ACK
```

三个包都出现，说明网络层、防火墙、目标服务全部正常，TCP 层连接没问题，问题（如果还有）在应用层。

### 模式一：只有 SYN，没有 SYN,ACK

```
Client → SYN
Client → SYN     (重传)
Client → SYN     (重传)
```

**含义**：客户端的 SYN 发出去了，但完全没有收到任何回应（包括拒绝）。

**故障域**：
- 包根本没到达对端（中间网络设备丢包、路由不通）
- 或者到达了对端，但对端防火墙**静默丢弃**（DROP，而不是 REJECT）—— 这是防火墙的典型行为，不回应任何东西，客户端只能看到超时重传

**排查方向**：
1. 在**客户端**抓包确认 SYN 真的发出去了（不是应用层根本没发起连接）
2. 在**目标服务器**上同时抓包，看 SYN 有没有到达
   - 服务器上完全没抓到 SYN → 问题在中间网络（路由器、云安全组、运营商）
   - 服务器上抓到了 SYN 但没回 SYN,ACK → 问题在服务器本机防火墙（DROP 规则）或服务没监听该端口

### 模式二：SYN 收到 RST（明确拒绝）

```
Client → SYN
Server → RST,ACK
```

**含义**：对端明确拒绝了这个连接，而不是沉默。

**故障域**：
- 目标端口没有进程在监听（最常见）—— 操作系统内核收到 SYN，发现没有服务监听该端口，直接回 RST
- 或者防火墙配置的是 **REJECT** 而不是 DROP（比如 `iptables -j REJECT --reject-with tcp-reset`）

**排查方向**：先用 `ss -lntup` 确认服务是否真的监听了这个端口（见 [[linux/网络排障/网络故障排查 Runbook.md]] 的第⑥步），排除服务未启动的可能，再看是不是防火墙主动拒绝

### 模式三：三次握手完成，但连接很快被 RST

```
Client → SYN
Server → SYN,ACK
Client → ACK
...（一段时间后）
Server → RST
```

**含义**：TCP 层连接建立成功了，但应用层很快主动断开了连接。

**故障域**：不再是网络问题，是应用层问题——服务端应用逻辑判断出了错误（比如认证失败、协议不匹配、限流），主动 reset 连接。这时候应该去看应用日志，而不是继续排查网络层。

### 模式四：握手成功，但后续数据传输卡住

```
Client → SYN
Server → SYN,ACK
Client → ACK
Client → PSH,ACK  (发送请求数据)
...（长时间没有响应）
```

**含义**：连接建立没问题，请求也发出去了，但迟迟等不到响应。

**故障域**：这不是网络连通性问题了，是**应用处理慢/卡死**，或者是**非对称路由**（去程和回程走了不同路径，回程被拦截）。非对称路由的典型特征：在客户端抓包看不到任何服务器的响应包，但在服务器端抓包能看到它确实发出了响应——这种情况要重点查中间的路由/防火墙是否只放行了一个方向。

## 双端同时抓包，是定位"在哪个环节丢的"的关键手法

单端抓包只能看到"我这边发了/没发/收了/没收"，没法确定问题发生在链路的哪一段。真正有效的做法是**在客户端和服务器同时抓包**，对比结果：

| 客户端看到 | 服务器看到 | 结论 |
|-----------|-----------|------|
| SYN 发出，无响应 | 完全没收到 SYN | 中间网络丢包/路由问题/云安全组拦截 |
| SYN 发出，无响应 | 收到了 SYN，但没回应 | 服务器本机防火墙 DROP，或服务未监听 |
| SYN 发出，收到 RST | （服务器上无需再看） | 服务器内核直接拒绝：端口未监听 或 防火墙 REJECT |
| SYN 发出，收到 SYN,ACK | 服务器发了 SYN,ACK 但客户端说没收到 | 非对称路由，回程被拦截 |

## 常用过滤表达式速查

```bash
# 只看 TCP 三次握手相关的包（SYN 或 ACK 标志位）
tcpdump -ni eth0 'tcp[tcpflags] & (tcp-syn|tcp-ack) != 0'

# 只看 RST 包（连接被拒绝/重置）
tcpdump -ni eth0 'tcp[tcpflags] & tcp-rst != 0'

# 抓某个源/目的 IP 的流量
tcpdump -ni eth0 src 192.168.1.10
tcpdump -ni eth0 dst 192.168.1.20

# 抓某个网段
tcpdump -ni eth0 net 192.168.1.0/24

# 组合条件：某主机的某端口
tcpdump -ni eth0 host 192.168.1.100 and port 443

# 排除某类流量（比如排除 SSH，避免抓到自己远程连接的噪音）
tcpdump -ni eth0 not port 22

# 抓 ICMP（ping 相关，排查网络层连通性）
tcpdump -ni eth0 icmp
```

## 实战流程建议

1. **先明确假设**：根据 [[linux/网络排障/网络故障排查 Runbook.md]] 前几步的结果，已经有一个大致的怀疑方向（比如"怀疑是服务器防火墙拦截"）
2. **双端同时抓包**：在客户端和服务器上同时起 `tcpdump`，然后触发一次连接尝试
3. **对照上面的判读表**：根据两端看到的报文差异，定位具体在哪个环节出问题
4. **验证后再动手改**：确认问题环节后（比如确认是防火墙 DROP），再去改对应配置，而不是盲改一通

## 提示

- `tcpdump` 默认只抓包头摘要，想看完整数据内容用 `-X`（十六进制+ASCII）或 `-A`（纯 ASCII，适合看明文协议如 HTTP）
- 长时间抓包容易产生巨量数据，生产环境建议加 `-c 数量` 限制包数，或者先用窄过滤条件（精确到 host+port）
- 抓包文件（`-w`）可以导出用 Wireshark 图形化分析，握手时序图看得更直观
- 没权限跑 `tcpdump`（需要 root 或 `CAP_NET_RAW`）时，`ss -i` 能看到部分 TCP 内部状态（重传次数、RTT等）作为退而求其次的手段
