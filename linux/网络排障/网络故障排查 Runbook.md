## 排障哲学

命令谁都能查，`ping`/`traceroute`/`ss` 怎么用一搜就有。真正值钱、能反复复用、几年后还有效的，是**证据链**——遇到问题时，按什么顺序收集证据、每一步的结果怎么判断、下一步去哪查。

这篇笔记记录的不是"命令怎么用"，是"我遇到网络故障时，应该按什么路径缩小故障域"。

## 排障决策树总览

```
网络故障
   │
   ├─ ① 本机网络正常吗？
   │    ip addr / ip link / ip route
   │
   ├─ ② 网关能到吗？
   │    ping <gateway> / ip neigh
   │
   ├─ ③ 外部 IP 能到吗？
   │    ping 1.1.1.1 / traceroute / tracepath
   │
   ├─ ④ DNS 正常吗？
   │    resolvectl / dig / nslookup
   │
   ├─ ⑤ TCP 端口通吗？
   │    nc -vz host port / curl -v
   │
   ├─ ⑥ 服务真的监听了吗？
   │    ss -lntup
   │
   ├─ ⑦ 防火墙拦了吗？
   │    nft list ruleset / iptables -L -n -v
   │
   └─ ⑧ 还定位不了？
        tcpdump（见 [[linux/网络排障/tcpdump 抓包排障.md]]）
```

**核心原则**：每一步都是在缩小"故障域"——从本机 → 局域网 → 广域网 → 应用层，一层层排除，而不是上来就抓包。抓包是最后手段，因为信息量大、需要更多解读成本。

## 逐层排查详解

### ① 本机网络正常吗？

**要回答的问题**：网卡有 IP 吗？网卡是 up 的吗？路由表对吗？

```bash
ip addr        # 看网卡有没有分配到 IP，有没有 UP 状态
ip link        # 看网卡链路层状态（UP/DOWN），网线有没有插好
ip route       # 看默认路由（网关）配置对不对
```

**判断逻辑**：
- 网卡状态是 `DOWN` → 物理层问题（网线、驱动、交换机端口）
- 网卡 `UP` 但没有 IP → DHCP 没拿到地址，或静态配置丢失
- 有 IP 但路由表没有默认路由（`default via ...`）→ 网关配置缺失，能通局域网但出不了网

**下一步**：本机正常 → 进入 ②；网卡异常 → 检查物理连接、DHCP 服务、网络配置文件

### ② 网关能到吗？

**要回答的问题**：能不能到局域网的下一跳？

```bash
ping <gateway_ip>     # 例如 ping 192.168.1.1
ip neigh              # 查看 ARP 表，看网关的 MAC 有没有解析出来
```

**判断逻辑**：
- `ping` 网关不通 + `ip neigh` 里网关状态是 `FAILED`/`INCOMPLETE` → ARP 没解析成功，可能是网线/交换机/网关本身故障
- `ping` 网关通 → 局域网链路正常，问题在网关之外

**下一步**：网关通 → 进入 ③；网关不通 → 排查物理链路、交换机、同网段是否有 IP 冲突

### ③ 外部 IP 能到吗？

**要回答的问题**：能不能出局域网、到公网？

```bash
ping 1.1.1.1              # 直接 ping 一个已知稳定的公网 IP（绕开 DNS 变量）
traceroute 1.1.1.1         # 看在哪一跳开始丢包/超时
tracepath 1.1.1.1          # 不需要 root 权限的替代品
```

**判断逻辑**：
- 网关通但外部 IP 不通 → 问题在网关到公网之间：上级路由器、运营商链路、NAT 配置
- `traceroute` 显示某一跳之后全部超时 → 大概率故障点就在那一跳（但注意有些设备会对 ICMP 限速/丢弃，不能 100% 当真）
- 外部 IP 通 → 网络层完全正常，进入 ④

**关键点**：这一步故意用 IP 而不是域名，排除 DNS 这个变量，纯测试网络层连通性。

### ④ DNS 正常吗？

**要回答的问题**：域名能不能解析成 IP？

```bash
resolvectl status         # 查看当前使用的 DNS 服务器配置（systemd-resolved 系统）
resolvectl query example.com   # 用当前配置解析一个域名
dig example.com            # 详细查看 DNS 解析过程和返回
dig example.com @8.8.8.8   # 强制用指定的 DNS 服务器解析，排除本地 DNS 配置问题
nslookup example.com       # dig 的简化替代品
```

**判断逻辑**：
- IP 通但域名不通 → 问题基本锁定在 DNS
- 用本地 DNS 解析失败，换 `@8.8.8.8` 能解析成功 → 本地/运营商 DNS 服务器有问题
- 换了公共 DNS 也解析失败 → 域名本身有问题（没解析记录、TTL 过期未刷新等），或者本机到该 DNS 服务器的网络不通

**下一步**：DNS 正常且 IP 正常 → 进入 ⑤（应用层排查，具体端口/服务）

### ⑤ TCP 端口通吗？

**要回答的问题**：目标端口有没有开放、能不能建立 TCP 连接？

```bash
nc -vz host port          # 快速测试端口是否可连接
# -v 显示详细过程，-z 不发送数据只测试连接（zero-I/O）

nc -l 8888                 # 反向用法：在本机临时监听一个端口，当靶子测试防火墙/路由通不通
curl -v https://host/     # 对 HTTP(S) 服务更直观，能看到连接、握手、请求全过程
telnet host port           # nc 的老牌替代品，效果类似
```

`nc`/`curl` 是**主动去连**，测的是"我能不能连上对方"；下一步的 `ss` 是**被动查看**，测的是"对方到底有没有在听"——两者是一对，配合起来看更准。

**判断逻辑**：
- 连接被拒绝（`Connection refused`）→ 目标端口没有服务在监听，或防火墙主动拒绝（RST）
- 连接超时（无响应）→ 大概率是防火墙丢包（不回应），或路由不通
- 连接成功 → TCP 层没问题，问题在应用层（HTTP 状态码、业务逻辑等）

**下一步**：端口通 → 应用层排查（看返回内容、状态码、日志）；端口不通 → 进入 ⑥ 和 ⑦

### ⑥ 服务真的监听了吗？

**要回答的问题**：（在服务器本机上）服务进程真的把端口起起来了吗？监听在哪个地址上？

```bash
ss -lntup                 # 列出所有监听中的 TCP/UDP 端口和对应进程，日常排障最常用这条
# l = listening, n = 不解析域名/服务名(更快更准), t = tcp, u = udp, p = 显示进程

ss -tan state established  # 看实际已建立的连接（不止监听），排查"连上了但异常"的场景

netstat -lntup              # ss 的前身，参数几乎照搬；容器等精简系统可能没装，装了就用 ss
```

**关键输出列**：`Local Address:Port` 是本机监听的地址；`Peer Address:Port` 在监听状态下永远是 `0.0.0.0:*`（还没有具体对端连进来）；`Process` 是占用该端口的进程名/PID。

**判断逻辑**：
- 端口根本没出现在列表里 → 服务没启动，或启动失败，去查服务日志
- `Local Address` 是 `127.0.0.1:port`（或 `127.0.0.53%lo:port` 这种回环写法）而不是 `0.0.0.0:port` 或具体网卡 IP → 服务只监听本地回环，外部当然连不上，这是配置问题
- 端口确实监听在正确的地址上，但外部还是连不上 → 问题在防火墙，进入 ⑦

**这一步的价值**：很多"网络问题"根本不是网络问题，是服务配置错误（监听地址错、服务没起来）。放在防火墙排查之前，能少走很多弯路。

### ⑦ 防火墙拦了吗？

**要回答的问题**：本机或中间设备的防火墙规则有没有挡住这个连接？

```bash
nft list ruleset          # nftables 规则（较新系统）
iptables -L -n -v          # iptables 规则（-v 显示命中计数，可以看到规则有没有被触发）
firewall-cmd --list-all    # firewalld 前端命令（RHEL 系）
ufw status verbose         # ufw 前端命令（Debian/Ubuntu 系）
```
（各防火墙工具的详细笔记见 [[linux/防火墙/防火墙总览.md]]）

**判断逻辑**：
- 用 `iptables -L -n -v` 反复执行同一个连接测试，看对应规则的计数器（packets/bytes）有没有增长 → 增长说明流量确实匹配到了这条规则，可以确认是这条规则在拦截
- 服务确实监听了、本机防火墙也放行了，还是连不上 → 问题可能在网络中间设备（云安全组、路由器 ACL、上级防火墙），不在本机

**下一步**：本机防火墙排除嫌疑后仍连不上 → 检查云平台安全组/ACL；如果所有配置检查都正常但现象诡异 → 进入 ⑧，直接抓包看真相

### ⑧ 还定位不了？上 tcpdump

到这一步，说明前面的间接证据（配置、日志、状态）已经不足以定位问题，需要直接看包在不在、有没有到、对端有没有回。详见 [[linux/网络排障/tcpdump 抓包排障.md]]。

## 案例：域名访问失败的完整判断树

这是最常见的真实场景，把上面几层串起来看效果：

```
域名访问失败
      │
      ├── ping IP 成功
      │      └── dig 域名失败
      │              ↓
      │          优先查 DNS（本地 resolv.conf / DNS 服务器 / 域名 TTL）
      │
      ├── IP 也不通
      │      ↓
      │   查路由/网关（回到 ①②③）
      │
      └── IP 通 + DNS 正常
             ↓
          nc 测端口
             │
        ┌────┴────┐
      不通        通
       ↓           ↓
  防火墙/服务    应用层排查（HTTP 状态码、业务日志）
  (⑥⑦)
```

**这张图的价值**：一开始不知道故障在哪一层，但只要按顺序测（先 IP 再 DNS 再端口），每测一步就排除一个可能性，故障域越缩越小，不用凭感觉瞎猜。

## 常见误区

- **一上来就抓包**：信息量太大，没有先验判断的话很难看出问题在哪。应该先用①-⑦缩小范围，再用 tcpdump 验证具体假设
- **只测一次就下结论**：偶发性问题（丢包率高但不是100%）需要多测几次，或者用 `mtr`（ping+traceroute结合，持续采样）代替单次 `ping`/`traceroute`
- **忽略 IPv4/IPv6 双栈问题**：现在很多系统同时有 v4/v6，域名解析出 v6 地址但 v6 路由不通，会表现得像"随机失败"。`curl -4`/`curl -6` 强制指定协议栈可以快速排除
- **防火墙测试后立刻改规则再测**：应该先用计数器确认是不是这条规则在拦截，再动手改，避免"改了但其实没解决"
