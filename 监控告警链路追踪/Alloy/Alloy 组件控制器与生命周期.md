 [[监控告警链路追踪/Alloy/Alloy 组件配置规则.md]] 提到"组件控制器负责依赖图增量更新、循环引用检测"，这篇展开控制器具体管什么、组件的健康状态怎么定义、配置怎么热重载。

## 控制器的四项职责

1. 读取并校验配置文件
2. 管理所有已声明组件的生命周期
3. 求值组件的参数（Arguments）
4. 上报组件的健康状态

前面笔记里讲的"依赖图增量求值""循环引用检测"，都是第 2、3 项职责的具体体现。

## 组件的四种健康状态

| 状态 | 含义 |
| --- | --- |
| `Unknown` | 组件刚创建、还没启动时的默认状态 |
| `Healthy` | 正常工作 |
| `Unhealthy` | 遇到错误或没有按预期工作 |
| `Exited` | 已经停止运行 |

健康状态由参数求值是否成功、运行时有没有报错、以及部分组件自带的健康检查逻辑共同决定。

**关键点：组件的健康状态和它引用的上游组件相互独立。** 哪怕引用的是一个 `Unhealthy` 组件的导出值，本组件自己照样可以是 `Healthy`——比如上游文件读取失败但用的是缓存的旧值，下游组件用这个旧值照常工作，不会被上游的故障状态传染。这也是排查问题时容易搞反因果的一点：看到某组件 Unhealthy，不代表下游全部跟着挂。

## 求值顺序：初始评估 vs 重新评估

**初始评估**（Alloy 刚启动或者重载配置后）严格分三步：

1. 依赖解析：先确定谁依赖谁
2. 并行求值：没有依赖关系的组件可以同时求值，不用排队
3. 组件创建并启动

**重新评估**：某个组件的导出值变化后，会自动触发下游的级联重新求值（[[监控告警链路追踪/Alloy/Alloy 组件配置规则.md]] 里"求值顺序"一节讲的三步走例子，就是这个级联机制的实例）。

## 配置热重载

两种触发方式：调用 `/-/reload` HTTP 端点，或者给 Alloy 进程发 `SIGHUP` 信号。

重载做三件事：

- 删除配置里不再声明的组件
- 创建新增的组件
- 对所有托管的组件重新求值

不需要重启整个 Alloy 进程，也不会打断没受影响的组件。

## 容错：优雅降级

如果某次求值失败（比如配置里引用的文件突然读不到了），组件**不会崩溃退出，而是继续用上一次成功求值时的配置**接着跑。这个设计防止一次局部故障（比如某个配置文件短暂不可读）级联拖垮整条监控链路——毕竟采集链路本身的可用性，往往比数据本身实时性更重要。

## 小结

控制器 = 配置解析器 + 依赖图调度器 + 健康状态上报器。四种健康状态里最容易误判的是"上游 Unhealthy 不代表下游也 Unhealthy"；热重载走 `/-/reload` 或 `SIGHUP`，不用整个重启；遇到求值失败会优雅降级用旧配置兜底，不是直接罢工。
