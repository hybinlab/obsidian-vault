## 核心认知：上下文是最重要的资源

官方最佳实践几乎都围绕一个约束：**上下文窗口会很快被填满，填得越满模型表现越差**。所以：

- 无关任务之间用 `/clear`；同一个问题纠正两次还不对，就 `/clear` 后写一个更好的提示词重来。
- 大量读文件的调研交给子代理（"use subagents to investigate X"），主会话只拿到摘要。
- 给 Claude 一个**能自己跑的验证手段**（测试、构建、截图对比），它才能自己闭环，而不是靠你肉眼检查。
- 复杂任务：**先探索 → 再计划（plan mode）→ 再实现 → 提交**；一句话能说清的改动就直接做，不用计划。

## 各种扩展分别解决什么问题

| 功能 | 作用 | 什么时候用 |
| --- | --- | --- |
| CLAUDE.md | 每次会话都加载的持久上下文 | 项目约定、"总是做 X" 的规则 |
| Output style | 设定回复的角色、语气、格式 | 想让回答更短/更详细/换个角色 |
| Skill | 按需加载的知识或可调用的工作流 | 可复用的流程（`/deploy`）、参考资料 |
| Subagent | 独立上下文里干活，只返回摘要 | 读大量文件的调研、并行任务 |
| MCP | 连接外部服务 | 查数据库、发 Slack、操控浏览器 |
| Hook | 在生命周期事件上**确定性地**执行脚本 | 每次编辑后跑 lint、拦截危险命令 |
| Plugin | 把上面这些打包分发 | 多个仓库共用同一套配置 |

几组容易混的：

- **CLAUDE.md vs Skill**：总要知道的放 CLAUDE.md（控制在 200 行内）；偶尔用到的参考资料或流程放 Skill。
- **Skill vs Hook**：Skill 是给 Claude 读的指令，结果可能有偏差；Hook 是一定会执行的脚本。**"绝不能做 X" 这类护栏要用 Hook**，写在 CLAUDE.md 里只是请求，不是保证。
- **Skill vs Subagent**：Skill 的内容进入当前上下文；Subagent 用独立上下文，只把结果带回来。

## 按需逐步加配置（官方建议的顺序）

| 触发信号 | 加什么 |
| --- | --- |
| Claude 同一个约定/命令错了两次 | 写进 CLAUDE.md |
| 总是要求它更简短或换格式 | 设置 output style |
| 反复输入同样的开场提示词 | 存成可调用的 Skill |
| 第三次把同一份操作手册贴进对话 | 做成 Skill |
| 总在从浏览器复制 Claude 看不到的数据 | 接一个 MCP 服务 |
| 某个支线任务的输出淹没了对话 | 交给 Subagent |
| 希望某件事每次都自动发生 | 写一个 Hook |
| 第二个仓库也要同样的配置 | 打包成 Plugin |

## 上下文成本

| 功能 | 何时加载 | 成本 |
| --- | --- | --- |
| CLAUDE.md | 会话开始，全文 | 每次请求都占 |
| Skill | 开始时只加载描述，用到时加载全文 | 低（设 `disable-model-invocation: true` 后描述也不加载） |
| MCP | 开始时只加载工具名，schema 按需 | 用到前很低 |
| Subagent | 被调用时 | 与主会话隔离 |
| Hook | 触发时在外部执行 | 零（除非 hook 输出内容回传） |

用 `/context` 查看当前上下文占用，`/context all` 看每个 MCP 工具占多少 token。
